# Treasury and room-art onboarding contract

This is a developer reference for **approved** additions to Kae's treasury, not authorization to create a gift, purchase it, or change Dawn's inventory. The existing room editor and quantity-tier visuals are shipped and must not be replaced.

## Existing boundaries

- `reward_requests` contains proposed gifts; `reward_shop` defines purchasable gifts; `kae_inventory` records ownership; `reward_ledger` records coin accounting. Only the authenticated `purchase_kae_reward` RPC may purchase a gift.
- The scene source catalog is `assets/room/scene-assets.json`; `npm run assets:build` generates `assets/scene-catalog.json`. **Never hand-edit the generated file.**
- The current catalog describes selectable scene assets, with `id`, `label`, allowed `slots`, `renderer`, optional `treasure`, `source` and `fit`. It is **not** a complete inventory-to-room renderer or a shop metadata catalog. In particular, the jewel catalog entry is a preview image; the owned jewel is rendered through existing room code.
- `scripts/build-scene-catalog.mjs` validates unique IDs, supported slots/renderers, local asset paths, file existence and basic SVG restrictions. It does **not** validate shop item existence or entitlement. A catalog entry must not be treated as evidence that a user owns an item.
- The existing individually adjustable room-object placement and visibility are authoritative. New art must preserve saved coordinates, visibility, ordering and the display-case glass layering. Do not revive the superseded fixed-shelf or chest/table coupling designs.

## Repeatable procedure for an approved gift

1. Confirm Dawn approved the specific gift, its name, price, repeatability and intended appearance. Check existing `reward_requests` and `reward_shop` for a matching item. A request is **not** a purchase.
2. Identify the existing `reward_shop.slug` and whether a matching room display already exists. Reuse existing art and mapping where possible. Do not assume that adding a scene-catalog row alone makes an owned treasure visible.
3. For an approved new art asset, add a local file under `assets/` and, if it belongs in the selectable scene editor, add its metadata to `assets/room/scene-assets.json`. Use the current allowed slot and renderer vocabulary. Do not introduce remote or executable asset URLs.
4. Run `npm run assets:build` and `npm test`; use `npm run test:browser` for any visible scene change. Review generated catalog diffs and test at phone and desktop dimensions. A catalog-only addition must not rewrite room layouts.
5. If a new owned-treasure renderer or quantity-tier mapping is necessary, implement and test that separately against actual ownership and current quantity boundaries. Do not infer ownership from the catalog, fabricate inventory, or change existing reward ledger rows.
6. Merge only after required checks pass and the implementation is reviewed. Confirm the merge and relevant deployment. Record real Android acceptance separately; CI or mocked browser tests are not proof of Dawn's phone experience.

## Reusable illustrated inventory path (November 28, 2026)

The browser already creates an independent movable `item:<shop-item-id>` room slot for an owned shop item without a dedicated static scene node. Do not add another permanent HTML element, bespoke CSS rule, or manually numbered layout slot for routine new collectible art.

- **One illustration:** add the approved local file, then an entry to `assets/room/scene-assets.json` with `id`, `label`, `slots: ["inventory_item"]`, `renderer: "inventory_image"`, `treasure: "<exact reward_shop.slug>"`, `source: "assets/...svg"`, and `fit: "contain"`. The scene generator validates its local image, unique slug, safe path and special renderer. This entry is not a layout-editor preview or a shop registration. The existing owned-item keyed room slot displays it automatically, but **only** when an actual positive-quantity inventory row exists.
- **Multiple quantity tiers:** add matching local SVGs and an entry keyed by the exact `reward_shop.slug` to `assets/treasure-quantity/manifest.json`. Populate all four current tier IDs (single, pile, mound, chest_or_bundle) and keep the existing 1–4, 5–12, 13–25 and 26+ boundaries. A tiered variant takes priority over a single-image registration; the generic inventory slot also uses tiers without new JS. The three established coin/jewel/whisker nodes retain their existing dedicated renderer and layouts.
- **No image ready:** the existing name-marker fallback remains. Missing/invalid catalogs do not authorize ownership or silently remove a purchased item. New images for approved shop slugs are a code-and-art release, not permission to invent or alter shop records, inventory, prices, purchases, ledger entries, or pending request status.
- **Verification:** `npm run assets:build`, `npm test`, `npm run test:browser`. Mock browser fixtures exercise unowned removal, image/tier selection, preserved independent slots and unchanged coin balance. The privileged shop fulfillment and request-to-shop link still require the separately authorized admin path and independent production readback. No publicly writable shop endpoint or new Bee capability is introduced.

## Privileged request-to-shop fulfillment handoff (BEE-REPEAT-01)

The ordinary signed-in Treasury UI may **submit or edit pending requests**, but it cannot approve them or register a shop item. This is deliberate: authenticated clients have no general shop INSERT/UPDATE permission and must not be given one to simplify onboarding. The private Bee plugin currently documents no Treasury fulfillment command. Fulfillment is an **explicit, privileged human/agent operation**, not an automatic effect of submitting a request. A responsible executor must carry each approved request through to independently verified availability.

1. **Establish approval and scope.** Read the request and verify Dawn's explicit approval of the gift, price, repeatability, design/artwork scope and whether a room visual is intended. If any essential choice is missing, leave the request pending and ask once; never interpret an old request, silence, or a dragon blurb as approval. Check existing requests and shop slugs to avoid duplicate gifts.
2. **Assign the handoff.** Record a concise request-specific checkpoint with the responsible executor, current request ID/status, proposed shop slug, approved decisions and next action in the Agent Runbook/roadmap. This avoids the previous gap where an approved request waited without an accountable fulfillment step. Do not claim a plugin API exists for this.
3. **Implement the approved gift.** Using an authorized privileged administrative path, register or reuse the approved shop record and matching slug. If artwork is required, follow the asset-build, scene registry, ownership-gated renderer and quantity-tier procedure above. Existing shop registration is not proof that a room object will render. Keep request, shop, inventory and ledger as separate records; do not fabricate purchases or grants.
4. **Link and reconcile.** Only after the shop entry is real and verified, link the request to the correct `shop_item_id` and mark it available using the authorized privileged path, with a short fulfillment note. Verify the request-to-shop join, active shop visibility, approved price/repeatability, unique slug and absence of unintended inventory/ledger changes. A pending request must not be silently dropped; a completed shop item must not be mistaken for ownership.
5. **Verify deployment and visuals.** Run `npm run assets:build`, `npm test`, and `npm run test:browser` where relevant; verify exact-head CI, merge SHA and matching GitHub Pages deployment for code/art changes. Independently check deployed asset URLs and shop availability. Test ownership-gated room rendering for visual gifts, including saved layout and glass layering; record Android acceptance separately when observed. If there is no art/code change, document that no Pages deployment was necessary rather than inventing one.
6. **Close the checkpoint.** Record request ID, linked shop ID/slug, approved price and repeatability, implementation PR/commit (if any), production checks, unresolved visual acceptance and the responsible executor's release of ownership. Move an implementation item to Completed only after its actual merge/deployment gates pass; do not infer end-to-end automation from a successful historical one-off.

**Existing-state sanity check (November 21, 2026):** All five historical reward requests are already `available` with linked active shop records, including Scale Oil. Do not re-register them or mistake this checklist for permission to change their prices, purchase state or art.

## Acceptance for a future generalized pipeline

A future onboarding improvement should make approved additions routine without duplicating bespoke room logic per collectible. It must preserve: owner-scoped shop and inventory records, explicit purchase authorization, ledger/history, quantity-tier display, saved independent placement and visibility, glass-case layering, and backward compatibility for existing treasures. Any migration affecting the installed Bee API or existing data needs a separate impact review.

## Illustrated room background previews and later shop linkage (November 28)

The chamber uses the original `assets/chamber-room.jpg` (with SVG fallback) by default. The two new, deliberately high-contrast concept settings live at `assets/room/backgrounds/moonlit-observatory.svg` and `mosslight-grotto.svg`, indexed by `assets/room/backgrounds/manifest.json`. Both are **preview-only concepts**, not registered gifts. They can be viewed in Settings → Adjust room layout → Room background without buying anything. Closing the editor restores the selected owned background or original room; concept previews never persist, cost coins or modify user layouts.

The art catalog deliberately separates production from selling: each manifest entry has a stable ID, title, local SVG/PNG/WebP/JPEG source, and nullable `shopSlug`. To later turn one into a real shop treasure, first agree on the background's name, price and availability; have the authorized fulfillment process register a `reward_shop` item with a unique slug and preserve any linked request. Then update that approved background's `shopSlug` to precisely match the existing shop item, deploy and verify. The normal purchase RPC and positive `kae_inventory` ownership gate persistent selection. No dedicated furnishing slot, new access rule, reward accounting or user-side shop insert required. A missing ownership row or invalid catalog leaves the previous/original background visible. Never use mere preview state or catalog presence as proof of a purchase.

Background choices are per-browser per-owner presentation preferences, distinct from saved object coordinates. A change to the visual background cannot displace, remove or grant a throne, crown, chest, floor object, jewel or other inventory item. The existing illustrated Kae image stays intact. When an owned skin is chosen, the app saves only its stable background ID, rechecking ownership on every inventory refresh; unowned art remains preview-only. More illustrated scenes can be added by inserting one local asset and one manifest entry without editing layout or shop purchase code.

The large compositional art style is intentionally different from the small fallback Kae expression sprites introduced in PR #98; those were not full illustrated Kae portrait variants. For new raster scenes, retain a 5:3 composition and the dragon's center-safe space, and test in the actual mobile room before claiming visual acceptance.
